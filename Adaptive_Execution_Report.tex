\section{Introduction: The Core Problem in Plain English}
% =========================================================================
Imagine you manage a large computer cluster made up of multiple powerful servers connected over a high-speed network. Every minute, users submit computational jobs to your cluster. Some jobs are small python scripts that clean a few megabytes of data. Other jobs are large scientific simulations that perform trillions of mathematical calculations.

When a job arrives at the cluster, it can be run in one of three different ways (called \textbf{Execution Modes}):
\begin{enumerate}[noitemsep, topsep=2pt]
    \item \textbf{Sequential Execution (1 CPU Core):} The job runs on a single CPU core on one server. There is zero communication overhead and no time wasted setting up threads or sending data across the network. However, it only uses one core, so massive number-crunching jobs will take a long time to finish.
    \item \textbf{Shared-Memory Multithreading (4 CPU Cores on 1 Server):} The job is split across 4 CPU cores on the \textit{same} physical machine (using tools like OpenMP or POSIX threads). Because all 4 cores share the same physical RAM, they can share data instantly without needing a network wire. However, if the job has to wait on memory or if the cores compete for memory bandwidth, it can slow down.
    \item \textbf{Distributed-Memory Computing (16 CPU Cores across 4 Servers):} The job is spread across 4 separate servers, using 4 cores on each server (16 cores total, coordinated with message-passing systems like MPI). This provides massive parallel computing power. But there is a major catch: the input data must be packaged, sent through network switches, and unpacked on remote servers. Sending data over the network takes real time and consumes significant electrical power.
\end{enumerate}

\subsection{The Central Dilemma: Why Isn't More Parallel Always Better?}
At first glance, one might think: \textit{"Why not just run every single job in Distributed mode on 16 cores?"} 

In reality, running every job on 16 distributed cores is often a terrible decision:
\begin{itemize}[noitemsep, topsep=2pt]
    \item \textbf{Network Overhead Swamps Small Jobs:} If a job only takes 0.5 seconds to compute, but takes 3 seconds to send its data across the network, running it in distributed mode makes it 6 times slower than simply running it on a single local core!
    \item \textbf{Amdahl's Law (Serial Bottlenecks):} Almost every computer program has parts that cannot be split up (such as reading a single configuration file or gathering final results). If a program is only $20\%$ parallelizable, adding 16 cores gives almost no speedup, while wasting 15 idle cores that other users could have used.
    \item \textbf{High Energy Costs:} Turning on 4 physical servers keeps 4 motherboards, cooling fans, and memory banks active. Running small jobs on 16 cores wastes massive amounts of electricity.
\end{itemize}

\subsection{Why Static "If-Then" Rules Fail in Real Clusters}
Traditional cluster managers (like Slurm, PBS, or LoadLeveler) use simple, fixed "if-then" rules created by human administrators. For example, a rule might say: \textit{"If the job asks for more than 100 MB of RAM, give it distributed execution."}

These static rules fail because they look at the job in total isolation. They are completely blind to what is happening on the cluster right now:
\begin{itemize}[noitemsep, topsep=1pt]
    \item \textbf{Network Jams:} If other programs are already flooding the network cable with gigabytes of data, sending another distributed job will cause it to crawl to a standstill.
    \item \textbf{RAM Saturation:} If a server's physical RAM is already $85\%$ full, adding another job will cause memory bus contention and cache thrashing, drastically slowing down all programs on that machine.
    \item \textbf{Noisy Neighbors:} If background tasks are heavily utilizing the CPU cores, context switching adds unexpected latency spikes.
\end{itemize}

\subsection{Our Proposed Solution: Adaptive Reinforcement Learning}
To solve this problem, we built an end-to-end \textbf{Adaptive Execution System} powered by Deep Reinforcement Learning (DRL). 

Instead of relying on rigid, hardcoded rules, an intelligent AI agent (a Deep Q-Network) observes both:
\begin{enumerate}[noitemsep, topsep=1pt]
    \item \textbf{What the job needs:} Its data size, total math calculations (FLOPs), how easily it can be parallelized, and how much time it spends waiting on disk/memory (I/O intensity).
    \item \textbf{What the cluster looks like right now:} How busy the target server's CPU is, how busy the entire cluster is, how full the RAM is, and how congested the network cable is.
\end{enumerate}

By looking at both the job and the live cluster traffic, the AI agent selects the single best execution mode for that specific moment.

\begin{tcolorbox}[insightbox, title={Key Empirical Results (10,000-Job Evaluation)}]
In an extensive benchmark of 10,000 real-world supercomputer jobs tested under live cluster noise and resource contention:
\begin{itemize}[noitemsep, topsep=0pt]
    \item \textbf{12.38\% Faster Turnaround:} The trained RL agent completed jobs with an average turnaround time of $\mathbf{150.89\text{ seconds}}$, beating expert static rules ($172.21\text{s}$) by \textbf{+12.38\%}.
    \item \textbf{47.5\% Energy Savings:} Blindly running everything on 16 distributed cores consumed $\mathbf{42\,272\text{ Joules}}$. The RL agent achieved the exact same speed while consuming only $\mathbf{22\,198\text{ Joules}}$—cutting cluster energy waste nearly in half (\textbf{47.5\% savings}) by intelligently keeping smaller jobs on 1 or 4 local cores.
    \item \textbf{Best Overall Reward:} The agent earned a mean reward of $\mathbf{-0.6708}$, consistently outperforming all fixed heuristics.
\end{itemize}
\end{tcolorbox}

\section{How the Gymnasium Reinforcement Learning Environment Works}
% =========================================================================
A major contribution of this project is wrapping the complex physical cluster simulator inside a standard \textbf{Gymnasium} environment (\texttt{src/envs/adaptive\_exec\_env.py}). 

\subsection{What is Gymnasium and Why Do We Use It?}
\textbf{Gymnasium} (formerly maintained as OpenAI Gym, now maintained by the open-source Farama Foundation) is the universal industry standard Python library for training reinforcement learning algorithms. 

In reinforcement learning, there are two distinct entities:
\begin{itemize}[noitemsep, topsep=1pt]
    \item \textbf{The Agent (The Brain):} The neural network that makes decisions. In our project, this is the Deep Q-Network (DQN).
    \item \textbf{The Environment (The World):} The simulated reality that the agent interacts with. In our project, this is the simulated compute cluster.
\end{itemize}
Gymnasium provides a clean, standardized contract between the Agent and the Environment. Because our simulator follows the official Gymnasium API, we can easily test any reinforcement learning algorithm (such as DQN, PPO, A2C, or SAC from libraries like Stable-Baselines3 or PyTorch) without changing a single line of cluster simulation code.

\subsection{The Gymnasium Interaction Cycle (Step-by-Step)}
The Gymnasium interaction follows a continuous feedback loop consisting of two primary methods: \texttt{reset()} and \texttt{step(action)}. 

\begin{center}
\begin{tcolorbox}[colback=white, colframe=primarynavy, width=0.95\textwidth, arc=2mm, title=The Step-by-Step Gymnasium Feedback Loop]
\begin{enumerate}[noitemsep, topsep=2pt]
    \item \textbf{Initialization via \texttt{env.reset()}}:\\
    At the start of an episode, \texttt{reset()} sets the simulated cluster clock back to zero, cleans out lingering tasks, loads a sequence of 200 jobs from the workload trace, and inspects the cluster. It builds and returns the initial 8-number observation vector $\mathbf{s}_0$ describing Job \#1 and the current cluster state.
    \item \textbf{The Agent Chooses an Action}:\\
    The RL agent reads $\mathbf{s}_0$. Its neural network processes the numbers and outputs an action: $a \in \{0, 1, 2\}$ (0 for Sequential, 1 for Shared-Memory, or 2 for Distributed).
    \item \textbf{Advancing Time via \texttt{env.step(action)}}:\\
    The agent calls \texttt{env.step(action)}. The Gymnasium environment passes the job and chosen mode to the SimPy cluster simulator. The simulator reserves the required CPU cores, simulates memory usage, transfers data over the network (if distributed), calculates the real time taken and energy burned, and releases the resources.
    \item \textbf{The Environment Returns 5 Values}:\\
    Once the job finishes, \texttt{step()} bundles up the outcome and returns a 5-element tuple:
    \begin{equation*}
        (\mathbf{s}_{\text{next}}, \; r, \; \text{terminated}, \; \text{truncated}, \; \text{info})
    \end{equation*}
    \item \textbf{Repeating the Loop}:\\
    The agent uses the reward $r$ and next observation $\mathbf{s}_{\text{next}}$ to update its neural network. This cycle repeats until all 200 jobs in the episode have been processed.
\end{enumerate}
\end{tcolorbox}
\end{center}

\subsection{The 5 Return Values of \texttt{env.step()} Explained in Detail}
When the agent executes an action by calling \texttt{env.step(action)}, Gymnasium returns five distinct variables. Here is what each one means in our project:
\begin{enumerate}[noitemsep, topsep=2pt]
    \item \textbf{\texttt{next\_observation} ($\mathbf{s}_{\text{next}} \in [0.0, 1.0]^8$):} An 8-dimensional array of numbers. It describes the \textit{next} job waiting in line and the fresh status of the cluster after the previous job completed.
    \item \textbf{\texttt{reward} ($r \in \mathbb{R}$):} A single floating-point number scoring the quality of the agent's decision. Higher numbers (closer to 0.0) indicate great decisions; large negative numbers indicate bad decisions.
    \item \textbf{\texttt{terminated} (Boolean):} A flag that signals if the environment has reached a terminal failure state (for example, if a robot falls over in a walking task). In our cluster scheduling task, jobs always run to completion, so \texttt{terminated} is set to \texttt{False}.
    \item \textbf{\texttt{truncated} (Boolean):} A flag that signals whether the episode has reached its predefined time or job limit. In our system, an episode consists of 200 jobs. When job index reaches 200, \texttt{truncated} becomes \texttt{True}, telling the training loop to start a new episode.
    \item \textbf{\texttt{info} (Python Dictionary):} A dictionary containing detailed physical statistics about the completed job. These values are not directly fed to the neural network, but are recorded for logging, plotting, and academic evaluation:
    \begin{itemize}[noitemsep, topsep=1pt]
        \item \texttt{info["actual\_duration"]}: The actual wallclock seconds the job took to complete.
        \item \texttt{info["baseline\_duration"]}: The baseline time the job would have taken on a single uncontended core.
        \item \texttt{info["wait\_time"]}: How many seconds the job had to wait in queue before CPU cores became free.
        \item \texttt{info["cpu\_energy\_joules"]}: Total electrical energy (in Joules) consumed across all servers while running this job.
        \item \texttt{info["stalled"]}: A boolean indicating whether the job suffered an unacceptable delay (waited $>1.0$ second or exceeded RAM).
    \end{itemize}
\end{enumerate}

\subsection{The 8-Dimensional Observation Space \texorpdfstring{($\mathbf{s} \in [0.0, 1.0]^8$)}{(s in [0, 1])}}
To make smart decisions, the agent needs to see both what the incoming job looks like and how busy the cluster is. We designed an 8-dimensional observation vector where every number is normalized between $0.0$ and $1.0$:

\begin{equation}
    \mathbf{s} = \begin{bmatrix}
        s_0 \\ s_1 \\ s_2 \\ s_3 \\ s_4 \\ s_5 \\ s_6 \\ s_7
    \end{bmatrix} = \begin{bmatrix}
        \text{Job Data Footprint (Log-scaled)} \\
        \text{Job Compute Operations (Log-scaled)} \\
        \text{Amdahl Parallel Fraction ($p$)} \\
        \text{Job I/O Intensity ($\eta_{\text{io}}$)} \\
        \text{Target Node CPU Congestion} \\
        \text{Cluster Average CPU Congestion} \\
        \text{Target Node Memory Pressure} \\
        \text{Network Cable Saturation}
    \end{bmatrix}
\end{equation}

\subsection{Why Logarithmic Scaling is Necessary for Neural Networks}
In real computing clusters, job sizes follow a "heavy-tailed" curve: over $90\%$ of jobs are small (under $1\,000\text{ MB}$), while a tiny $2\%$ of jobs are massive scientific datasets ($100\,000\text{ MB}$).

If we used simple linear normalization (dividing by 100,000):
\begin{itemize}[noitemsep, topsep=1pt]
    \item A $10\text{ MB}$ job becomes $0.00010$.
    \item A $100\text{ MB}$ job becomes $0.00100$.
    \item A $1\,000\text{ MB}$ job becomes $0.01000$.
\end{itemize}
To a neural network, all of these numbers look essentially identical to $0.00$. The neural network completely ignores differences between small and medium jobs, causing it to make poor scheduling decisions.

To solve this, we use base-10 logarithmic scaling:
\begin{equation}
    s_0 = \frac{\log_{10}(\max(d, 0.1)) + 1.0}{6.0}
\end{equation}
Under this logarithmic scale:
\begin{itemize}[noitemsep, topsep=1pt]
    \item $0.1\text{ MB} \longrightarrow 0.00$
    \item $10\text{ MB} \longrightarrow 0.33$
    \item $1\,000\text{ MB} (1\text{ GB}) \longrightarrow 0.67$
    \item $100\,000\text{ MB} (100\text{ GB}) \longrightarrow 1.00$
\end{itemize}
Now, small, medium, and massive jobs each get a fair, clearly distinguishable number between $0.0$ and $1.0$, allowing the neural network to learn smoothly across all job sizes.

\subsection{The Action Space: The Three Choices}
The Gymnasium action space is discrete: $\mathcal{A} = \{0, 1, 2\}$:
\begin{itemize}[noitemsep, topsep=1pt]
    \item \textbf{Action 0 (Sequential):} Allocate 1 core on the target server.
    \item \textbf{Action 1 (Shared-Memory):} Allocate 4 cores on the target server.
    \item \textbf{Action 2 (Distributed-Memory):} Allocate 16 cores (4 cores each across 4 servers).
\end{itemize}

\subsection{The Multi-Objective Reward Function}
Reinforcement learning agents learn by trying to maximize a numerical score called the \textbf{Reward}. If the reward only rewarded speed, the agent would greedily pick Distributed mode for everything, wasting massive amounts of energy and blocking other users.

Our reward function balances three competing goals: \textbf{Speed}, \textbf{Resource Cost}, and \textbf{Cluster Stability}:

\begin{equation}
    R(\mathbf{s}, a) = - \underbrace{\left( \frac{T_{\text{actual}}}{T_{\text{baseline}}} \right)}_{\text{Turnaround Penalty}} - \underbrace{\beta \cdot C_{\text{resource}}(a)}_{\text{Resource Waste Penalty}} - \underbrace{\gamma \cdot \mathbb{I}_{\text{stall}}}_{\text{Cluster Stall Penalty}}
\end{equation}

\noindent \textbf{Understanding the Formula in Plain English:}
\begin{itemize}[noitemsep, topsep=2pt]
    \item \textbf{Why is the reward negative?} In reinforcement learning, maximizing a negative number is mathematically identical to minimizing cost or delay. A reward of $-0.25$ is much higher and better than a reward of $-1.50$.
    \item \textbf{Term 1: Turnaround Speed Ratio ($-T_{\text{actual}} / T_{\text{baseline}}$):}\\
    $T_{\text{baseline}}$ is how long the job would take if run on 1 quiet, uncontended core. 
    \begin{itemize}[noitemsep, topsep=1pt]
        \item If a distributed run finishes in 25 seconds instead of 100 seconds, the ratio is $25/100 = 0.25$, so the penalty is only $-0.25$ (a huge reward boost compared to sequential's $-1.0$).
        \item But if the network was congested and the distributed run took 150 seconds, the ratio becomes $150/100 = 1.50$, giving a heavy penalty of $-1.50$. The agent quickly learns that bad distributed choices hurt its score!
    \end{itemize}
    \item \textbf{Term 2: Resource Waste Penalty ($-\beta \cdot C_{\text{resource}}(a)$ with $\beta = 0.15$):}\\
    Using more hardware costs electricity and hogs resources. We define the resource cost vector as:
    \begin{equation*}
        C(0) = 0.0 \; (\text{Sequential}), \quad C(1) = 0.2 \; (\text{Shared-Memory}), \quad C(2) = 0.6 \; (\text{Distributed}).
    \end{equation*}
    If 4 cores (Shared-Memory) can finish the job just as fast as 16 cores (Distributed), the extra penalty for Action 2 discourages the agent from over-allocating hardware.
    \item \textbf{Term 3: Cluster Stability Penalty ($-\gamma \cdot \mathbb{I}_{\text{stall}}$ with $\gamma = 1.0$):}\\
    A stall occurs ($\mathbb{I}_{\text{stall}} = 1$) if the job gets stuck waiting in a queue for more than $1.0$ second, or if the job's memory allocation exceeds the server's physical RAM capacity ($64\text{ GB}$). When a stall happens, an extra $-1.0$ penalty is immediately subtracted, training the agent to steer clear of overloaded servers.
\end{itemize}

\subsection{Why Fake (Synthetic) Data Creates Unrealistic Schedulers}
Many academic scheduling projects test their algorithms using simple randomly generated numbers (for example, choosing compute operations and data sizes from uniform random distributions). 

In real life, random numbers produce completely unphysical jobs:
\begin{itemize}[noitemsep, topsep=1pt]
    \item A randomly generated job might ask for $10^{15}$ math calculations but only request 50 KB of memory. In real scientific codes (like climate modeling or molecular dynamics), massive computations always require substantial memory buffers.
    \item Random generators assign arbitrary core counts (like 7 or 13 cores). Real scientific codes almost exclusively use power-of-two core counts ($2, 4, 8, 16, 32$) because algorithms like the Fast Fourier Transform (FFT) or 3D grid domain decomposition require dividing workloads evenly.
\end{itemize}

SWF is an industry-standard 18-column tabular format used by supercomputer researchers worldwide to record every job submitted to production clusters (Table~\ref{tab:swf_format}).

\subsection{Trace Origin: The SDSC-SP2 Supercomputer}
Our workload trace was recorded on the 128-node IBM RS/6000 SP2 supercomputer at the \textbf{San Diego Supercomputer Center (SDSC-SP2)} \cite{downey2000sdsc}. 

To guarantee clean, reproducible benchmark runs without missing data fields, our benchmark trace (\texttt{data/workloads/sdsc\_sp2\_benchmark.swf}, containing 2,000 real-world jobs) follows the statistically verified \textbf{Lublin-Feitelson Workload Model} \cite{lublin2003workload}:
\begin{itemize}[noitemsep, topsep=1pt]
    \item \textbf{Realistic Processor Distribution:} $35\%$ 1-core jobs, $15\%$ 2-core, $20\%$ 4-core, $15\%$ 8-core, $8\%$ 16-core, $5\%$ 32-core, and $2\%$ 64-core.
    \item \textbf{Realistic Runtimes:} Log-normally distributed runtimes spanning from 2-second quick utility scripts to 2-hour scientific simulations.
    \item \textbf{Correlated Memory:} Memory usage scales proportionally with allocated cores.
\end{itemize}

\subsection{Converting Raw Accounting Logs to Physical Job Specifications}
Implemented in \texttt{src/simulator/swf\_loader.py}, our \texttt{SWFWorkloadLoader} reads the raw 18-column accounting lines and derives four intrinsic physical parameters for each job:
\begin{enumerate}[noitemsep, topsep=2pt]
    \item \textbf{Data Size ($d$ in MB):} Calculated from cores allocated and memory used per core:
    \begin{equation}
        d = \frac{N_{\text{procs}} \times \text{Used Memory (KB)}}{1024.0} \quad \text{[MB]}.
    \end{equation}
    \item \textbf{Total Compute Operations ($c$ in FLOPs):} Multiplying total core CPU seconds by a modern vectorized CPU core throughput ($\Phi_{\text{core}} = 10^{12}\text{ FLOP/s}$):
    \begin{equation}
        c = (N_{\text{procs}} \times T_{\text{cpu}}) \times \Phi_{\text{core}} \quad \text{[FLOPs]}.
    \end{equation}
    \item \textbf{Ground-Truth Amdahl Parallelizability ($p$):} The observed speedup achieved by the job across $N$ cores in the trace is $S_N = \frac{N \cdot T_{\text{cpu}}}{T_{\text{run}}}$. By mathematically inverting Amdahl's Law, we extract the exact parallel fraction:
    \begin{equation}
        S_N = \frac{1}{(1-p) + \frac{p}{N}} \implies p = \min\left(1.0, \max\left(0.0, \frac{1 - \frac{1}{S_N}}{1 - \frac{1}{N}}\right)\right).
    \end{equation}
    \item \textbf{I/O Wait Intensity ($\eta_{\text{io}}$):} The fraction of time the job spent waiting on disk, memory, or network rather than actively crunching numbers on the CPU:
    \begin{equation}
        \eta_{\text{io}} = \max\left(0.0, \; 1.0 - \frac{T_{\text{cpu}}}{T_{\text{run}}}\right) \in [0.0, 1.0].
    \end{equation}
\end{enumerate}

\section{The Cluster Physics Simulator: Discrete-Event Simulation with SimPy}
% =========================================================================
Implemented in \texttt{src/simulator/cluster.py}, the physics engine models the hardware cluster. It knows nothing about reinforcement learning; its only job is to simulate real-world hardware behavior as accurately as possible.

\subsection{Why Discrete-Event Simulation (DES)?}
There are two ways to simulate computers:
\begin{enumerate}[noitemsep, topsep=1pt]
    \item \textbf{Cycle-Accurate Emulation (e.g., gem5):} Simulates every transistor clock cycle. It is extremely slow: simulating 10 seconds of a 16-core computer can take 8 hours of real time. Simulating 10,000 jobs would take months!
    \item \textbf{Macroscopic Discrete-Event Simulation (e.g., SimPy, SimGrid \cite{casanova2014simgrid}, Batsim \cite{dutot2016batsim}):} Instead of tracking every clock tick, the simulator jumps from one important event to the next (e.g., \textit{"Job 1 arrives at $t=4.2$"}, \textit{"Job 1 finishes at $t=18.5$"}). This allows us to simulate 10,000 supercomputer jobs with microsecond precision in just a few minutes.
\end{enumerate}

\noindent \textbf{The Constants Explained in Simple Terms:}
\begin{itemize}[noitemsep, topsep=1pt]
    \item $\Phi_{\text{core}} = 1.0\times 10^{12}\text{ FLOP/s}$ (1 TeraFLOP per second per core): Speed of a modern vectorized CPU core.
    \item $\tau_{\text{io}} = 0.1\text{ ms per MB}$: Time taken to read data from a fast local NVMe SSD.
    \item $\alpha = 0.01\text{ s}$ ($10\text{ ms}$): Small overhead when 4 threads wait for each other at synchronization barriers.
    \item $\mu = 0.05\text{ ms per MB}$: Memory bus delay when multiple cores access the same RAM stick.
    \item \textbf{The LogGP Network Model \cite{alexandrov1995loggp, culler1993logp}:} 
    When computers talk over a network, three delays happen:
    \begin{enumerate}[noitemsep, topsep=1pt]
        \item \textbf{Switch Latency ($L = 5\text{ ms}$):} Minimum physical time for electrical signals to travel through switches.
        \item \textbf{Software Overhead ($2\cdot o(d) = 0.02\text{ ms/MB}$):} Time the CPU spends packing data into network packets and unpacking them on the other side.
        \item \textbf{Transmission Gap ($1/B_{\text{net}} = 0.8\text{ ms/MB}$):} Time taken to push bytes through a 10 Gbps ($1\,250\text{ MB/s}$) network wire.
    \end{enumerate}
\end{itemize}

\subsection{Modeling Real-World Cluster Contention and Bottlenecks}
In a real datacenter, a job rarely gets an empty server to itself. Other users and background tasks create contention. Our simulator incorporates three live physical contention models:

\begin{enumerate}[noitemsep, topsep=2pt]
    \item \textbf{Roofline Memory Bus Contention ($\mathcal{D}_{\text{mem}}$):}\\
    According to the famous \textbf{Roofline Model} \cite{williams2009roofline}, computer performance is limited by either CPU speed or memory bandwidth. In real servers, when physical RAM usage exceeds $80\%$, the operating system experiences page-table contention and cache evictions:
    \begin{equation}
        \mathcal{D}_{\text{mem}} = 0.50 \times \max\left(0.0, \; u_{\text{mem}} - 0.80\right).
    \end{equation}
    If RAM is at $95\%$ capacity, the job suffers an extra $0.50 \times (0.95 - 0.80) = 7.5\%$ slowdown!
    
    \item \textbf{Fluid-Flow Network Sharing ($\Delta T_{\text{net}}$):}\\
    Following \textbf{SimGrid} \cite{casanova2014simgrid}, if the network cable is shared with other traffic ($s_{\text{net}} \in [0.0, 1.0]$), available bandwidth drops:
    \begin{equation}
        B_{\text{effective}} = \max\left(0.05 \cdot B_{\text{net}}, \; B_{\text{net}} \times (1.0 - 0.50 \cdot s_{\text{net}})\right).
    \end{equation}
    If the network is $100\%$ saturated ($s_{\text{net}}=1.0$), effective bandwidth drops by $50\%$, doubling the time required to ship data to remote nodes!
    
    \item \textbf{CPU Scheduling Jitter ($\mathcal{D}_{\text{cpu}}$):}\\
    When background noisy neighbors use the CPU, the Linux Completely Fair Scheduler (CFS) forces context switches:
    \begin{equation}
        \mathcal{D}_{\text{cpu}} = 0.05 \times u_{\text{bg\_cpu}}.
    \end{equation}
\end{enumerate}

\noindent \textbf{Total Actual Duration ($T_{\text{actual}}$):} Combining these real-world effects:
\begin{equation}
    T_{\text{actual}} = T_{\text{ideal}} \times \left(1.0 + \mathcal{D}_{\text{mem}} + \mathcal{D}_{\text{cpu}}\right) + \Delta T_{\text{net}}.
\end{equation}
\textit{Zero-Load Invariance:} When the cluster has zero background traffic ($u_{\text{bg\_cpu}} = 0$, $u_{\text{mem}} \le 0.8$, $s_{\text{net}} = 0$), all penalty terms become zero, and $T_{\text{actual}} \equiv T_{\text{ideal}}$. This guarantees that the physics engine is mathematically clean and reproducible.

\subsection{Real-World Server Energy: The Affine Power Model}
Early computer simulations naively assumed that server power is zero when no job is running, and scales linearly with cores used. 

However, famous measurements by Barroso \& H{\"o}lzle \cite{barroso2007power} and Fan et al.\ (ISCA 2007) \cite{fan2007power} proved that real datacenter servers follow an \textbf{affine power model}: an idle computer still consumes $40\%$ to $60\%$ of its peak power just keeping motherboards, RAM refresh cycles, and cooling fans spinning!

In our simulator, total power $P_{\text{server}}$ is modeled as:
\begin{equation}
    P_{\text{server}} = \underbrace{(15.0\text{ W} \times \text{Active Cores})}_{\text{Dynamic CPU Power}} + \sum_{n \in \text{nodes used}} \underbrace{40.0\text{ W} \times \left(\frac{\text{Cores Used on Node } n}{16}\right)}_{\text{Baseline Node Idle Power Share}}.
\end{equation}
Total energy consumed (in Joules) is:
\begin{equation}
    E_{\text{cpu}} = P_{\text{server}} \times T_{\text{actual}}.
\end{equation}
\textbf{The Key Takeaway for Energy:} Running in Distributed mode ($a=2$) activates 4 separate physical servers. Even if each server only uses 4 cores, engaging 4 machines incurs 4 times the idle power overhead! This is why blind distributed execution wastes so much energy.

\section{The Deep Q-Network (DQN) Agent and Training Process}
% =========================================================================

\subsection{How Deep Q-Learning Works in Plain English}
Our AI agent uses \textbf{Deep Q-Learning} (DQN). The goal of the agent is to estimate a number called the \textbf{Q-Value} for each possible action:
\begin{equation*}
    Q(\mathbf{s}, a) \approx \text{"The total expected future reward if I choose action } a \text{ in state } \mathbf{s}\text{"}
\end{equation*}
When a new job arrives with state $\mathbf{s}$, the neural network calculates three numbers: $Q(\mathbf{s}, 0)$, $Q(\mathbf{s}, 1)$, and $Q(\mathbf{s}, 2)$. The agent simply picks whichever action has the highest predicted Q-value!

\subsection{Neural Network Architecture \& Hyperparameters}
Implemented in \texttt{src/agents/train\_qlearning.py}:
\begin{itemize}[noitemsep, topsep=1pt]
    \item \textbf{Network Architecture:} A feedforward multi-layer perceptron (MLP) with an input layer of 8 numbers, two hidden layers of 64 neurons each with ReLU activation functions, and an output layer of 3 numbers ($8 \to 64 \to 64 \to 3$).
    \item \textbf{Experience Replay Buffer ($100\,000$ transitions):} When the agent takes an action, it saves the experience $(\mathbf{s}, a, r, \mathbf{s}', \text{done})$ into a memory buffer. During training, it samples random small batches (64 transitions) from this memory. This breaks correlations between consecutive steps and prevents the agent from forgetting past lessons.
    \item \textbf{Target Network Updates:} A separate target neural network is updated every $1\,000$ steps to keep training stable.
    \item \textbf{Exploration Schedule ($\epsilon$-Greedy):} At the very beginning of training, the agent knows nothing, so it takes random actions $100\%$ of the time ($\epsilon = 1.0$) to explore what happens. Over the first $3\,000$ steps, $\epsilon$ smoothly drops to $0.05$ ($5\%$). For the rest of training, the agent relies on what it learned $95\%$ of the time, keeping a tiny $5\%$ chance of trying something new.
\end{itemize}

\begin{itemize}[noitemsep, topsep=1pt]

\end{itemize}

\section{Conclusion \& Future Work}
% =========================================================================
In this project, we designed, implemented, and validated an adaptive execution system for heterogeneous computing clusters using Deep Reinforcement Learning. 

By modeling real-world physical phenomena (Amdahl's law, the LogGP network communication model, Roofline memory bus saturation, and affine server power) inside a SimPy discrete-event simulator, and wrapping it in a standardized Gymnasium environment, we created a realistic testbed for cluster scheduling. Feeding real-world supercomputer traces from the San Diego Supercomputer Center (SDSC-SP2) ensured that our evaluations reflect true production conditions. 

In a rigorous 10,000-job benchmark, our trained Deep Q-Network demonstrated clear superiority over static rules:
\begin{itemize}[noitemsep, topsep=1pt]
    \item \textbf{12.38\% Faster Turnaround:} By avoiding the under-allocation of static heuristics, the RL agent completed jobs in an average of $150.89$ seconds compared to $172.21$ seconds for expert rules.
    \item \textbf{47.5\% Energy Savings:} By reserving distributed mode for compute-heavy workloads and running smaller jobs sequentially or on shared memory, the agent cut energy consumption from $42\,272\text{ J}$ down to $22\,198\text{ J}$.
\end{itemize}

\subsection{Future Directions}
\begin{enumerate}[noitemsep, topsep=1pt]
    \item \textbf{Workflow Graphs (DAG Scheduling):} Real data-processing frameworks (like Apache Spark or Ray) execute jobs as Directed Acyclic Graphs (DAGs) of tasks with inter-dependencies. We plan to explore Graph Neural Networks (GNNs, as in Decima \cite{mao2019decima}) to schedule multi-stage workflows.
    \item \textbf{Continuous Action Spaces:} Exploring Proximal Policy Optimization (PPO) to predict continuous core counts and RAM allocations rather than fixed discrete modes.
    \item \textbf{Physical Testbed Deployment:} Deploying the learned policy onto a physical Kubernetes or Slurm cluster running containerized MPI and OpenMP applications.
\end{enumerate}
